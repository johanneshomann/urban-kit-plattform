# Implementation Plan

## Overview

Replace the standalone `teams` collection and the boolean `isTeam` membership flag with a member-tagged, project-scoped team model: the project defines a team catalog, members are tagged with teams, and content can be scoped to a union of teams via `visibilityTeams[]`.

### Why
The current model has a dead `teams` collection (`visibilityTeam` fields exist on every content collection but **nothing evaluates them**), and "TEAM" visibility is decided by a single boolean (`isTeam` / PM). This makes team-scoped content (e.g. news for a steering group only) impossible. The new model gives the project manager (or any content creator) the ability to scope a single content item to "public, project, or a specific set of people".

High-level approach:
- **`project-memberships`**: drop `isTeam`; add `teams: (text)[]` — a membership is tagged with 0..n team names.
- **`projects`**: add `teams: (text)[]` — the team **catalog** (source of truth, PM-managed vocab) the membership tags and content scopes reference.
- **Content collections (news, calendar-events, polls, forum-threads, tasks, file-uploads, folders)**: change `visibility` from `PUBLIC|INTERNAL|TEAM` to `PUBLIC|PROJECT|TEAM`, and replace the single `visibilityTeam` relationship with `visibilityTeams: (text)[]`. `PUBLIC` ≈ current `PUBLIC`; `PROJECT` ≈ current `INTERNAL`; `TEAM` is only visible to active members whose `teams` intersect the doc's `visibilityTeams` (PM sees all).
- **`teams` collection**: delete (and remove from `payload.config.ts`).
- **`visibility.ts`**: rework from a 3-tier scalar model to membership-driven checks (`getViewerTier` → `{ tier, teams }`; new `canViewContent(membership, doc)` and `visibilityWhere(membership)` helpers).
- **Guards / queries**: update `getProjectTeamContext`, `getWorkspaceContext`, public project page, workspace module list/detail queries, and all manage-actions that read/set visibility; update the members manage UI/action to edit `teams` instead of `isTeam`.
- **Docs**: update `docs/access-control.md`, `docs/modules.md`, AGENTS.md (hard rule 5 and the visibility-model description), and run `npm run generate:types`.

### Decisions (confirmed with user)
- Team catalog is **project-level** on `Projects` (not free-form).
- Content scoping is **multiple teams via union** (`visibilityTeams: text[]`).
- `TEAM` content without `visibilityTeams` entries falls back to the pre-existing behavior: any active member with `teams.length > 0` (or PM) sees it — i.e. empty `visibilityTeams` ≈ old `TEAM` tier, so existing data stays meaningful.
- `Polls` keeps its `status` (draft/active/closed) untouched — only visibility semantics change.
- `event-attendees`, comments, nested polls structures, chat, board-canvases: **no** `visibilityTeams` field (comments inherit from their parent; board gets a `visibility` field for consistency as a second commit). Board-canvases is excluded from this plan's scope, but will gain `visibility` in a follow-up.
- Data migration is **optional after the first commit** (see steps 8+); the app tolerates legacy `INTERNAL` docs by treating them as `PROJECT`.

## Types

Single sentence describing the type system changes.

**New/changed TypeScript shapes (implemented in collections, re-generated by `npm run generate:types`):**

```ts
// Visibility (content collections + media + folders)
type Visibility = 'PUBLIC' | 'PROJECT' | 'TEAM'
// stored legacy 'INTERNAL' values are tolerated on read (mapped to 'PROJECT')

// --- project-memberships (replaces isTeam) ---
interface ProjectMembership {
  // …existing fields…
  isTeam: never // removed
  teams: string[] // team tags (intersect with project.teams catalog)
}

// --- projects (new team catalog) ---
interface Project {
  // …existing fields…
  teams: string[] // PM-managed vocab, e.g. ['Kernteam', 'Lenkungsgruppe']
}

// --- content collections (news, calendar-events, polls, forum-threads, tasks, file-uploads, folders) ---
interface ScopedContent {
  visibility: Visibility // default 'PROJECT'
  visibilityTeams: string[] // required-listed teams when visibility === 'TEAM'; ignored otherwise
}

// --- visibility.ts viewer context ---
interface ViewerMembership {
  id: string | number
  status?: string | null
  role?: string | null
  teams?: string[] | null
}
type ViewerContext = { tier: 'public' | 'member' | 'team'; teams: string[] }
```

Validation rules:
- `visibilityTeams` entries must be within the owning project's `teams` catalog (validated in manage-actions; the PM UI selects from the catalog).
- PM sees all content regardless of `teams` (implicit full access, matches current behavior).
- `status !== 'active'` → tier `public` (no teams).

## Implementation Order

Single sentence describing the implementation sequence.

Numbered steps (logical order to avoid conflicting edits, each commit-isolatable):

1. **Collections layer**: Edit `ProjectMemberships.ts` (add `teams`, drop `isTeam`), `Projects.ts` (add `teams` catalog), remove `visibilityTeam`/add `visibilityTeams`+`visibility` enum change in the 7 content collections, delete `src/collections/Teams.ts`, remove from `src/payload.config.ts`. Run `npm run generate:types`.
2. **Visibility core**: Rework `src/lib/visibility.ts` (`getViewerContext`, `canViewContent`, `visibilityWhere`, keep `viewerTier`/`getViewerTier` thin wrappers).
3. **Guards**: Update `src/lib/access/project.ts`, `src/lib/auth/requireProjectManager.ts`, `src/lib/workspace-context.ts` to the `{ tier, teams }` model.
4. **Manage actions**: Update `src/actions/manage/news.ts`, `calendar.ts`, `polls.ts`, `forum.ts`, `members.ts` (+ optional `settings.ts` for catalog), validate `visibilityTeams` against project catalog.
5. **Public + workspace queries**: Update `src/app/[locale]/(public)/projekte/[slug]/page.tsx` and workspace `m/[moduleType]/...` pages to use new `visibilityWhere`.
6. **UI**: Member management team-multiselect, project team-catalog editor, content-form visibility Teams multiselect.
7. **i18n**: Add `teams`, `visibilityTeams`, `visibility.PROJECT/TEAM` labels to `messages/de.json` + `messages/en.json` (key-identical).
8. **(Optional data migration)** `scripts-tmp/migrate-visibility.mjs`: flip legacy `INTERNAL` docs → `PROJECT`; legacy `TEAM` docs with no `visibilityTeams` keep `TEAM` (fallback to any-tagged).
9. **Docs**: Update `docs/access-control.md`, `docs/modules.md`, `AGENTS.md` (rule 5 + pattern inventory), optional `docs/architecture.md` route note.
10. **Verify**: `npx tsc --noEmit`, `npm run generate:types`, smoke-test public page + workspace + manage; commit granularly (collections / visibility core / guards / actions / UI / i18n / docs).
